# 开发学习工作流

- 英文原文（Agent 阅读）：`Docs/Learning/Workflow.md`

## 目的

Dream of Padma 既是游戏项目，也是全栈游戏开发课程。学习依附于已批准的项目交付物，但功能完成与学习者掌握程度分别衡量。

项目假设学习者可能从零开始。Agent 用清晰语言解释前置知识，展示真实证据，并保留让用户亲自操作工具的机会。

## 一个任务，两类结果

每个实现任务产生：

1. **项目结果：**满足任务契约、经过测试并可 Review 的产物。
2. **学习结果：**证明用户可以识别、操作、解释或迁移一至两个概念的证据。

Agent 可以完成第一类结果，但不能仅凭自己的代码或资源能运行，就声称用户已经掌握第二类结果。

## 学习闭环

```text
定位 -> 预测 -> 观察 -> 练习 -> 验证 -> 复述 -> 迁移
```

### 1. 定位

说明当前玩家侧需要、负责它的子系统、输入输出，以及为什么本任务先于后续内容。只介绍本任务必需的术语。

### 2. 预测

运行测试、修改数据、打开调试器或点击 Play 之前，先让用户说明预期结果。书面预测能成为用户心智模型的证据。

### 3. 观察

展示最小的有用产物：一个头文件契约、数据行、蓝图图边界、动画状态、Gameplay Debugger 视图、日志分类、RenderDoc/Insights Trace、材质节点组或测试输出。不要把定位变成整个引擎的参观。

### 4. 练习

用户亲自完成一个安全、可恢复的操作。例如修改受控数据值、设置断点、运行指定自动化测试、检查 Gameplay Tag、分析一帧捕获、修复一个测试样例，或复现一项文档化 Editor 操作。

### 5. 验证

把观察结果和预测对照，解释因果链和一个常见故障。如果练习修改不应成为项目内容，应恢复受控值。

### 6. 复述

用户用自己的话说明：

- 这个概念做什么；
- 它在 Padma 中属于哪里；
- 它不能依赖什么；
- 如何识别一种故障。

### 7. 迁移

提出一个相邻应用问题，例如带种子的随机如何影响存档、输入模式如何影响 UI 和 Gameplay，或 Niagara 预算如何改变内容制作。迁移能避免只记住一组点击步骤。

## 证据与状态

| 状态 | 含义 | 最低证据 |
|---|---|---|
| `Not started` | 尚无结构化接触 | 无 |
| `Introduced` | 已解释用途和术语 | 定位笔记和问题记录 |
| `Practiced` | 用户完成计划操作并检查结果 | 用户操作及可观察输出 |
| `Demonstrated` | 用户能解释概念，并应用到原示例之外 | 成功复述、迁移回答和证据 |

必须分别记录：

- Agent 产生的产物/测试证据；
- 用户产生的操作或观察；
- 用户的预测和复述；
- 误解和未决问题；
- 下一个前置知识或迁移练习。

截图和日志可以支持证据，但只有复制的命令输出、没有解释，不代表掌握。

## 职责拆分

| 参与者 | 职责 |
|---|---|
| Primary Agent | 安全交付功能，并保留可学习的接口 |
| `learning_tutor` | 限制概念范围、讲解前置知识、定义练习/证据并检查复述 |
| Review 者 | 确认学习工作没有破坏架构、测试或任务范围 |
| 用户 | 作出设计决定、亲自操作、提出问题并证明理解 |
| 集成协调者 | 确保证据被记录，并在任务之间安排前置知识顺序 |

## 选择学习目标

每个任务最多选择两个主要目标。最好一个是系统概念，一个是工具或证据技能。例如：

| 开发产物 | 合适的聚焦目标 |
|---|---|
| 核心日历值和测试 | `USTRUCT`/值语义；自动化测试边界样例 |
| 数据驱动卡牌定义 | Data Asset 与运行时实例；Gameplay Tag 与校验 |
| Encounter 行动时间轴 | 状态机/事件顺序；确定性场景测试 |
| ACT 卡牌选择模式 | Enhanced Input 上下文/输入门；时间膨胀与 UI/Gameplay 分离 |
| 战斗回滚 | 快照身份/版本化；存档往返验证 |
| Niagara 技能特效 | 发射器/系统所有权；特效预算检查 |
| World Partition 内容切片 | 流送单元所有权；可复现 Editor 验证 |
| 性能任务 | Unreal Insights 捕获；从假设到测量的推理 |

不要因为动画、物理、渲染、UI、网络、AI、音频、打包和工具都在总课程中，就把它们全部塞进一个任务。完整课程通过多个里程碑中的真实垂直切片覆盖。

## 对零基础友好的任务顺序

每遇到一个新模块或专业领域，按以下顺序：

1. 术语和所有权图；
2. 最小可工作产物；
3. 可观察的测试或调试器证据；
4. 一个受控故障及诊断；
5. 用户练习和复述；
6. 与一个相邻子系统集成；
7. 后续再深入性能、生产和边界情况。

这样能避免高级引擎功能变成与游戏架构无关的孤立教程。

## 学习何时阻塞任务完成

只要任务契约没有要求 `Demonstrated`，即使用户学习目标只有 `Introduced` 或 `Practiced`，项目结果也可以进入 `Verified`。不得虚假关闭学习证据，应把下一项练习带入后续任务。

反过来，也不能为了完成一个很宽的知识点而不断扩大实现 Goal。如果缺少的练习需要完全不同的产物，应建立后续学习专项任务或集成任务。
