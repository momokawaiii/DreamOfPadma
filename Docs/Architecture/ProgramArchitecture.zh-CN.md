## 1. 目的与权威范围

本文档定义如何把 Dream of Padma 的设计意图转化为可维护的 Unreal 实现。它负责程序结构、运行时所有权、模块边界、数据流、集成接口和工程变更控制。

它不替代策划案。策划案定义游戏是什么意思，本文档定义程序如何表示和执行这些含义。玩法或规则变化必须先修改对应的英文策划案或规则文档；只有当它影响实现方式时，才同步映射到本文档。

高层 MVP 策划与架构基线已于 2026-09-02 通过用户验收。架构可以为后续扩展建立接口，但不能自行补充明确标记为开放、提案、延期或需要试玩验证的规则和数值。

## 2. 当前实现与目标架构

### 当前项目状态

- Unreal Engine 关联版本为 UE5.8。
- 当前项目只有一个生成的运行时模块：DreamOfPadma。
- 下列模块目录是逻辑边界和文档归档位置，不是要求现在立即创建空的 UE 模块。
- 第一阶段应先在当前模块内部建立边界；只有当边界拥有稳定负责人或独立构建/测试需求时，才拆分成 UE 模块。

### 目标逻辑模块

    PadmaCore
        ^
        |
    PadmaGameplay   PadmaWorld   PadmaUI
          \            |           /
                 PadmaGame

PadmaGame 是组合根。箭头表示允许的依赖方向：Gameplay、World、UI 依赖 Core 契约，Game 负责组合运行时。具体 Unreal Build.cs 如何拆分，属于后续结构性决策。

## 3. 架构原则

1. 所有命令进入应用/规则层。UI、GM 工具、测试和未来网络消息使用同一套命令契约。
2. 规则服务验证命令、修改权威状态，并发出结果和明确事件。
3. 表现层消费状态和事件。Widget、动画、Niagara、音频和镜头不能重新定义规则。
4. 静态定义与可变本局状态分离。资产描述可能存在的内容，运行时状态描述当前游戏。
5. 卡牌、节点、遭遇、剧情事件、结局和存档记录使用稳定 ID。Actor 和 UObject 指针不能作为存档身份。
6. 合成、战斗、AI、先手以及任何需要复现的结果都使用确定性的随机流。
7. 跨模块契约必须小而有类型。不能创建万能 Manager 或没有边界的全局事件总线。
8. 组合根负责协调生命周期，但不能变成规则上帝对象。
9. 内容进入可玩版本前必须经过数据校验。
10. 架构决策在成为难以逆转的依赖前必须记录。

## 4. 运行时命令流

    玩家输入 / GM 命令 / 自动化测试 / 未来网络请求
                              |
                              v
                         命令契约
                              |
                              v
                       应用服务或规则服务
                              |
               +--------------+--------------+
               |                             |
               v                             v
           验证与修改状态                  计算结果
               |                             |
               v                             v
           权威状态  -----------------> 领域事件
                                             |
               +-----------------------------+------------------+
               |                             |                  |
               v                             v                  v
             UI / HUD                    AI 反应           存档 / 回放 / 遥测

每个修改状态的命令必须具有：

- 稳定的命令名称。
- 明确的输入结构。
- 在调试版本中可见的验证失败原因。
- 涉及随机时可复现的确定性结果。
- 状态变化或事件列表。
- 测试路径和人工复现路径。

示例包括移动、节点占领、B 卡附着、合成预览、合成执行、进入遭遇战、结算行动条窗口、结束遭遇战回合、打出基础非 A 战斗卡、在战斗外发动 ABC 卡技能、打开共享卡牌仓库、切换仓库页面、进入 ACT 子弹时间、打出战斗卡槽、切换控制模式、提交/回滚战斗事务和存档请求。

## 5. 运行时所有权

| 关注点 | 逻辑负责人 | 说明 |
|---|---|---|
| 卡牌、日历、资源、合成规则 | PadmaCore | 尽可能使用纯契约和确定性计算。 |
| 当前本局状态与跨关卡会话 | PadmaGame，状态类型来自 Core | GameInstance 生命周期；不能由 UI 持有真相。 |
| 共享沙盘和节点状态 | PadmaWorld | 稳定节点 ID 和世界变化事件。 |
| 当前局部战斗、行动条和战斗模式状态 | PadmaGameplay，由 PadmaGame 编排 | 遭遇战行动条状态和 ACT RealTimeAction 状态是两种独立局部模式；战斗规则与表现分离。 |
| 统治者策略 | PadmaGameplay | MVP 使用可复现的效用/优先级策略。 |
| 输入和 ViewModel | PadmaUI | 把输入转换为命令，消费结果/事件。 |
| 存档和读档编排 | PadmaGame；模式类型来自 PadmaCore | 保存稳定 ID 和版本化状态，不能保存 Actor 指针。 |
| 资源制作和校验 | PadmaEditor | 仅编辑器使用，不能成为运行时依赖。 |
| 自动化测试和夹具 | PadmaTests | 测试调用与正式玩法相同的命令和规则路径。 |

如果一个系统需要访问另一个系统的数据，应使用有类型的查询、命令、结果或事件。不能为了省略契约而暴露可变内部状态。

## 7. 数据驱动架构边界

设计层描述数据的游戏含义。DataDrivenArchitecture.md 描述资产选择、加载、校验、版本和运行时转换。模块文档描述哪个模块消费每份契约。

最小数据链路是：

    规则和数据含义
             |
             v
    类型化资产 / DataTable / CurveTable / GameplayTag
             |
             v
    资产校验与注册
             |
             v
    不可变运行时定义
             |
             v
    规则服务与可变本局状态
             |
             v
    结果、事件、存档记录和表现

如果某个平衡系数、卡牌身份、结算阈值或时代修正本来就应该由内容调整，模块不能把它隐藏在玩法代码中。

## 8. 阶段与玩法集成

MVP 日历是显式的：

    一天 = 黎明 -> 上午 -> 黄昏
    七天 = 一个时代
    七个时代 = 一个 Chapter

玩家循环是：

1. 黎明处理每日开始效果、到达、手牌刷新、配置资源和明确属于每日的恢复。
2. 上午接受沙盘移动、放置、B 卡附着或单独打出、合成、部署、建造、剧情选择和符合条件的 ABC 卡主动技能。
3. 统治者策略根据状态进行巡逻、侦测、增援和反攻。
4. 满足世界条件时可在任意日历阶段进入遭遇战。遭遇战是带条件行动条的回合制；场地和卡牌技能可以改变先攻、优先级、反应、打断、额外行动和非回合窗口。基础非 A 卡在每个符合条件的玩家行动回合最多打出一张。
5. 满足世界条件时也可以进入 ACT RealTimeAction 路线。ACT MVP 中点击 `Tab` 打开卡牌仓库、使背景虚化、划出五张卡，将世界时间降至 1/10，并禁止移动和攻击输入。此时只接受基础非 A 卡输入，场景保持惯性，数字卡槽分发基础非 A 卡效果。第一个 MVP 必须完成一轮 ACT 战斗闭环。
6. 两类局部战斗都作为独立事务运行：进入时暂停沙盘时间，记录所有被战斗修改的本局状态的完整版本化快照；胜利时提交结果，失败或退出时精确恢复该快照，再通过类型化结果和事件返回沙盘。在规则含义相同的地方，共用同一套权威服务处理效果、伤害、状态和结局。
7. 黄昏处理延迟效果、牌堆转换、威胁与熵变化和日终检查。
8. 如果没有结算结果，在安全边界存档并进入下一天。

行动条的精确优先级和数值时序、敌我共同的交战路线结算数据，以及 ABC 主动技能是否也能在局部战斗中发动，仍属于策划评审项。但已经确定：结算后的交战路线可以触发/选择 Encounter、ACT 或未来的其他 RealTimeAction 表现模式，也可以影响剧情推进。ABC 主动技能默认可以从 Sandbox 发动，但受每个技能的特殊限制约束。

## 9. 结算

MVP 已确定的两种主要胜利是：

- 统治者核心生命降为零。
- 战争天平达到玩家侧胜利边界。

架构使用一个通用结算器，而不是两个硬编码的结束分支。它读取启用的结算定义，对权威状态执行有类型的条件检查，处理同时满足条件时的优先级，发出 OutcomeResolved 事件，锁定本局结果，并保存结局 ID。

同一套契约也可以表示失败条件，但不会因此增加第三种胜利。信仰崩塌、主题胜利等级以及文档规定的其他胜负方式保留为未来兼容数据，除非明确启用。

结算规则由数据驱动架构描述，由 PadmaGame/PadmaCore 消费。结算器不能由 Widget、地图 Actor 或单张卡牌拥有。

## 10. 持久化、回放与未来网络权威

- 存档模式独立于 Actor 和关卡。
- 存档应包含模式版本、构建信息、种子/随机流位置、日历、全局资源、稳定的世界状态、卡牌状态、遭遇状态、剧情旗标、事件历史或等价历史引用，以及结束时的结局 ID。
- 第一目标是安全边界存档和战前回滚快照。动画中途和战斗中存档需要另外稳定的快照契约。
- 未来服务器拥有权威状态变化。客户端提交命令并接收结果/事件。
- 同一套确定性规则服务应可被本地玩法、GM 命令、自动化、回放验证和未来服务器调用。
- 联机不是 MVP 功能，但公共契约不能假设所有调用者都在本地。

## 11. 调试与校验

开发版和测试版必须显示：

- 命令 ID、来源和失败原因。
- 计算使用的数据定义 ID 和版本。
- 随机种子、流名称和投掷 ID。
- 资源、熵、信仰、威胁、战争天平和核心值的前后状态。
- 合成候选分数、Softmax 概率、成功率和西格玛/失败后果结果；合成失败必须显示没有奖励。
- AI 候选决策、分数、最终动作和原因。
- 每个结算条件的检查结果及获胜条件 ID。

校验层级：

1. 文档和模式审查。
2. 编辑器资产校验。
3. 纯计算和边界值单元测试。
4. 通过命令路径运行自动化测试。
5. PIE 冒烟测试。
6. 生产管线受影响时进行 Development 打包冒烟测试。

## 12. 设计模式使用

只在能澄清所有权时使用模式：

- Command：玩家、GM、回放和未来网络请求。
- Strategy：伤害、合成评分、AI 策略和目标选择。
- State：日历阶段、遭遇战行动条和战斗/控制模式。
- Observer/事件订阅：UI、剧情、音频和任务反应。
- Factory/Registry：数据定义的表现创建。
- Adapter：沙盘、遭遇战、RealTimeAction、鼠标、键盘、手柄、ACT 和 FPS 输入。
- Facade：Game 边界的组合。
- Composite：数据定义的效果序列。

模式不能授权 Singleton、Service Locator 或不受限制的全局访问。

## 13. 架构变更控制

以下变化必须有 ADR：

- 新增逻辑模块或 UE 模块。
- 修改依赖方向。
- 修改公共数据模式或稳定 ID。
- 修改存档模式。
- 修改网络权威边界。
- 从手工数据切换到导入管线。
- 让未来功能成为当前运行时依赖。

架构师 Agent 负责基线。模块 Agent 通过自己的模块文档提出局部变化。Review Agent 检查依赖方向和契约兼容性。改变规则含义时由策划负责人批准。

## 14. 实现顺序

1. 保留当前单一 UE 模块，先建立目录边界。
2. 实现 Core 值类型、ID、命令、结果、事件和确定性测试夹具。
3. 加入最小数据目录和校验路径。
4. 实现一个沙盘图和世界变化路径。
5. 实现一条合成预览/执行路径。
6. 实现一次遭遇、一次统治者响应和一个结算器。
7. 加入存档/读档和战前自动存档。
8. 加入 UI/ViewModel 表现和调试追踪。
9. 当边界被负责人、构建或测试需求证明后，再拆分 UE 模块。

## 15. 架构验收

满足以下条件后，架构基线可以进入实现：

- 每个 MVP 职责都有唯一负责模块。
- Core 不依赖表现层或具体世界 Actor。
- 静态定义、本局状态、事件和存档数据有明确区别。
- 合成和结算可以脱离 Widget 运行。
- 输入、GM 命令和测试可以调用同一条命令路径。
- 资产扩张前已经定义 ID 和版本规则。
- 跨模块变化有 ADR 和 Review 负责人。
- 每个模块 README 都说明当前状态和边界。
